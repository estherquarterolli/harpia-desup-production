Estas são as tarefas que dependem de você (banco, variáveis de ambiente, testes, commit).
Contexto: a porta do Postgres do Supabase está bloqueada na rede da unidade (só 443) — por isso
migrations no banco vão pelo **SQL Editor** do Supabase. Commits são feitos por você.

## 1. Aplicar a migration dos atalhos (`core.0002_atalhodashboard`)

É a **única** migration nova (a feature de atalhos criou a tabela `core_atalhodashboard`).
As demais correções (CORR-004 etc.) só mexeram em código/properties — **sem** migration.

### Opção A — se você tiver acesso ao banco por uma máquina/rede sem bloqueio
```bash
cd project_root
DJANGO_SETTINGS_MODULE=config.settings.production ../.venv/Scripts/python.exe manage.py migrate core
```

### Opção B — Supabase SQL Editor (porta bloqueada; recomendado aqui)
Cole e rode no **SQL Editor** do projeto Supabase:
```sql
BEGIN;

CREATE TABLE "core_atalhodashboard" (
    "id" bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    "chave" varchar(80) NOT NULL,
    "ordem" integer NOT NULL CHECK ("ordem" >= 0),
    "criado_em" timestamp with time zone NOT NULL,
    "user_id" bigint NOT NULL
);
ALTER TABLE "core_atalhodashboard"
    ADD CONSTRAINT "core_atalhodashboard_user_id_chave_04eb6245_uniq" UNIQUE ("user_id", "chave");
ALTER TABLE "core_atalhodashboard"
    ADD CONSTRAINT "core_atalhodashboard_user_id_8a784412_fk_accounts_user_id"
    FOREIGN KEY ("user_id") REFERENCES "accounts_user" ("id") DEFERRABLE INITIALLY DEFERRED;
CREATE INDEX "core_atalhodashboard_user_id_8a784412" ON "core_atalhodashboard" ("user_id");

-- registra a migration como aplicada (senão o Django tenta rodar de novo)
INSERT INTO django_migrations (app, name, applied)
VALUES ('core', '0002_atalhodashboard', NOW());

COMMIT;
```
Confirmação: `SELECT * FROM core_atalhodashboard;` (tabela vazia = ok) e
`SELECT * FROM django_migrations WHERE app='core' ORDER BY id DESC;` (deve listar `0002_atalhodashboard`).

> Se rodar o SQL **e** também rodar `manage.py migrate` depois, tudo bem — o registro em
> `django_migrations` faz o Django pular a 0002 (não duplica).

## 2. Variáveis de ambiente da observabilidade 500 (CORR-005)

Definir no **ambiente onde o backend está hospedado** (a confirmar — **não é o Render**; procurar o
host de produção real e setar lá as env vars). Sem `ADMINS_EMAILS` o e-mail de erro não dispara
(o resto continua logando em console/arquivo).

| Variável | Obrigatória | Exemplo / default |
|---|---|---|
| `ADMINS_EMAILS` | sim (p/ e-mail de erro) | `Dev Harpia <voce@exemplo.com>,ops@exemplo.com` |
| `SERVER_EMAIL` | opcional | remetente dos erros (default = `DEFAULT_FROM_EMAIL`) |
| `ADMIN_EMAIL_INCLUDE_HTML` | opcional | `False` (default; `True` = traceback HTML no e-mail) |
| `DJANGO_LOG_LEVEL` | opcional | `INFO` (default) |

**SMTP** (necessário para o e-mail sair de fato no host de produção — o default `localhost:25` não envia):
`EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`.

Teste do e-mail (staging/prod, `DEBUG=False`): forçar um 500 numa rota de teste e conferir se chega
o e-mail aos `ADMINS` + aparece em `logs/errors.log`/console. Em dev (`DEBUG=True`) o e-mail é
inerte de propósito (só console/arquivo) — não precisa de SMTP.

## 3. Testar localmente antes de commitar

Servidor de dev (usa o `.venv` da raiz):
```bash
cd project_root
DJANGO_SETTINGS_MODULE=config.settings.development ../.venv/Scripts/python.exe manage.py runserver
```
Checklist manual das mudanças desta rodada:
- **Atalhos (dashboard DESUP):** só "Adicionar atalho" no 1º acesso → abrir pop-up, marcar 1+ →
  Salvar (toast "Atalho(s) salvo(s)") → clicar no chip navega → "×" abre pop-up → Remover (toast).
  2º usuário DESUP não vê atalhos do 1º. (Requer a tabela do passo 1.)
- **CORR-002:** alocação → selecionar "Sem professor" mostra rótulo "Sem professor" (não fica vazio).
- **CORR-003:** alocação com matriz longa → dropdown de docente nas últimas linhas não é cortado
  (abre para cima quando falta espaço).
- **CORR-004:** parecer DESUP → aprovar TCC e indeferir extensão do mesmo professor → **sem 500**.
- **CORR-005:** `500.html` não afirma mais "equipe notificada".

Suíte automatizada (rápida por app):
```bash
DJANGO_SETTINGS_MODULE=config.settings.development ../.venv/Scripts/python.exe manage.py test apps.core apps.courses apps.extra_curricular
DJANGO_SETTINGS_MODULE=config.settings.development ../.venv/Scripts/python.exe manage.py check
```

## 4. Branch + commit (você)

Sugestão de fluxo (nada foi commitado ainda; tudo está no working tree):
```bash
git status                          # revisar arquivos alterados
git checkout -b feat/atalhos-e-corr-002-005
git add -A
git commit -m "feat: atalhos dashboard DESUP + CORR-002/003/004/005"
git push -u origin feat/atalhos-e-corr-002-005
```
Se preferir separar por correção, dá para fazer commits menores (ex.: um para a feature de atalhos,
um por CORR). Os arquivos de cada item estão listados nos relatórios em `docs/relatorios/`.

4. Criar branch e commitar (passo 4).
